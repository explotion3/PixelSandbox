# PixelSandbox 文档约定

- 项目根目录 `README.md` 是统一阅读与运行入口；项目资料集中在 `docs/`，不再维护项目外的分析目录。
- `Demo内容方案.md` 保存本项目玩法，区分已确定方向与可调整提案；`技术框架与性能.md` 集中保存当前实现、长期架构、性能目标及后续顺序。
- `工程验证.md` 按需简记有价值的新验证结果、复现方式、日志位置与未解决问题，注明日期和范围。普通内部修复可在交付说明中报告结果，不强制追加验证章节；不重复抄录完整日志、历史检查清单和未变化的实现边界，不把历史记录或文档格式检查写成新一轮游戏验证。
- `Noita原版/世界基础系统.md` 是原版总览；材料、角色、战斗、物品、敌人各保留一篇完整专题。正文、例子、未知项和来源放在同篇，不按组件拆分。
- 原版分析与本项目设计分开；区分本地证据、开发者历史说明、社区记录和未知项，不把推测写成原版实现。
- 修改 Markdown 前阅读 `C:/Users/ahhh/.codex/skills/obsidian-markdown/SKILL.md`；其他 Obsidian 文件按需阅读对应 skill。
- 开头先写关键结论，沿系统流程解释；中文、简洁。新增内容先并入对应专题，避免增加零散进度文档。
- 专题保留 `title`、`aliases`、`tags`、`type`、`created`、`updated`。专题之间用唯一名称的 wikilinks；项目入口、源码和日志可用相对 Markdown 链接；外部资料用普通链接，同篇来源优先脚注。
- `Noita原版/附录_区域索引.csv` 只作检索；`历史版本/` 只保留归档，不作为当前设计依据。
- 仅检查本次修改涉及的格式、链接和引用；相关 YAML、脚注、表格或路径发生变化时检查对应部分。需要视觉确认且 Obsidian 阅读视图可用时检查，不为普通文本修改启动应用或更改设置。未修改的专题、资产与来源不做全量审计，不为少量文档修改新建审计脚本。
- 按变化更新对应资料：操作或阅读入口变化更新根 README，架构与设计约定变化更新技术文档，玩法方向变化更新 Demo 方案；普通内部修复不要求同时修改这些文件。锁定版本变化时更新引用该版本的说明，版本以 `tools/versions.json` 和构建配置为准。

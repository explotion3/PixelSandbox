# Noita 世界基础系统

专题：[[材料、地形与物理]] · [[角色与环境]] · [[战斗与能力组合]] · [[物品、资源与成长]] · [[敌人与世界生态]]。

> [!abstract] 先抓住这条主线
> **区域地图决定哪里是什么区域 → 模板生成地形和场景 → 分块管理材料更新 → 组件驱动角色与物品 → 存档保留世界变化。**

| 要理解的问题 | 原版的关键做法 |
|---|---|
| 世界如何布局？ | 普通模式先读一张 **70×48 的区域地图**，区域内部再随机生成。 |
| 地形为什么既随机又眼熟？ | **Wang 模板拼接＋局部预制场景＋内容随机化**。 |
| 世界这么大，为什么能运行？ | **512 大块管理世界，64 小块调度材料模拟**，只更新活跃部分。 |
| 角色、物品怎样工作？ | 地形由材料像素组成；角色和物品使用**实体、组件与脚本**。 |
| 离开或退出后怎样接续？ | 除种子之外，还需要保留**实际变化、实体状态和全局状态**。 |

本文只讲原版世界底座。材料物理、角色环境、战斗组合、物品成长与敌人生态的详细分析见页首专题。依据为本地资源、游戏附带文档与公开技术说明；未确认的内部细节集中列在文末。

## 1. 世界如何布局：区域地图、地块和材料像素

这几个尺度承担不同工作：

| 层级 | 大小或形式 | 作用 |
|---|---|---|
| **区域地图 Biome Map** | 普通模式为 70×48 地图像素 | 每种颜色对应一种区域配置，例如矿坑、雪地或岩壁。 |
| **世界大块** | 512×512 世界像素 | 区域定位，以及流式生成、加载和存储的组织单位。 |
| **模拟小块** | 64×64 材料像素 | 缩小需要扫描和并行更新的范围。 |
| **地形模板 Wang Tile** | 预制局部片段 | 决定通道、洞穴、平台等空间结构；不能与前两种块混为一谈。 |
| **材料像素 Cell** | 一个材料网格单元 | 记录该处是什么材料，接受移动、破坏或转化等规则。 |

**区域地图决定“这里属于什么地方”，模板决定“这里长什么样”，材料决定“这里能发生什么”。**

普通模式的入口为 `magic_numbers.xml` 中的 `BIOME_MAP`。它指向 `scripts/biome_map.lua`，后者设置地图大小并读取 `biome_map.png`。地图颜色由 `_biomes_all.xml` 映射到具体区域 XML。[^layout]

因此，普通模式有相对稳定的大区域骨架，变化主要来自区域内部。新游戏+另有修改区域图的脚本，不能直接套用普通模式的布局结论。

> [!example]- 世界坐标怎样定位到区域地图
> 普通地图的横向原点在中间，纵向偏移 `biome_offset_y=14`。[^coordinates]
>
> ```text
> chunk_x = floor(world_x / 512)
> chunk_y = floor(world_y / 512)
> map_x   = chunk_x + 35
> map_y   = chunk_y + 14
> local_x = world_x - chunk_x * 512
> local_y = world_y - chunk_y * 512
> ```
>
> 世界 `(1098,824)` → 大块 `(2,1)` → 区域图 `(37,15)`。
> 世界 `(-1,-1)` → 大块 `(-1,-1)`，局部坐标 `(511,511)`；这里必须向下取整。
> 这套换算用于普通主世界，地图外范围与其他模式需另行处理。

## 2. 地形如何生成：先拼空间，再填内容

以矿坑为例，它的配置把三个入口连接起来：[^generation]

```text
coalmine.xml
  ├─ Topology：使用 BIOME_WANG_TILE
  ├─ wang_template_file：指定地形模板图
  └─ lua_script：指定 coalmine.lua 的生成函数
```

**第一步是生成空间骨架。** 人工制作的局部片段通过人字形 Wang Tiles 按匹配约束拼接，组合成通道、平台和洞穴。开发者选择这种方法，是为了保留空间设计的控制力，同时减弱普通方格拼接的接缝感。匹配约束本身不代表已经完成整张地图的可达性检查。[^wang]

**第二步是确定材料与生成位置。** 模板图中的颜色承担三类工作：

| 颜色用途 | 配置入口 | 结果 |
|---|---|---|
| 直接表示材料 | `materials.xml` 的 `wang_color` | 对应位置填入指定材料。 |
| 表示生成标记 | `RegisterSpawnFunction(颜色,函数)` | 在该世界位置调用函数，例如生成宝箱、油罐或祭坛。 |
| 表示可替换区域 | `RandomMaterials`、`color_material` 等 | 同一模板可以填入不同材料，形成变体。 |

灰度模板区域还可以结合区域 `<Materials>` 配置转成具体材料；矿坑配置中可见材料阈值、稀有分布和深度限制。模板并非只有一种简单的“颜色→材料”解释。[^generation][^coordinates]

**第三步是加入局部场景和实体。** Pixel Scene 将材料结构、外观和背景分别描述；固定大场景还会分片后放到指定世界坐标。地图里的内容不全来自随机拼接，也包含固定位置的预制结构。[^scenes]

> [!example] 一个油罐标记怎样产生变化
> 矿坑的 `load_oiltank` 先进行一次 50% 分支，选择油罐场景池或另一组场景池；随后再按权重选择具体场景，罐内填充材料还可以继续变化。[^generation]
>
> 所以随机发生在多个层次：**地形片段 → 局部场景 → 场景变体 → 内部材料**。

脚本里的 `prob` 通常是**相对权重**，不能直接当百分比。`is_unique=1` 在该表实例中被选中后会将其权重置零；这不等于已经确认全世界永久唯一。[^helpers]

## 3. 世界如何运行：分块驻留，局部更新

世界规模与每帧工作量通过两层机制分开处理：

- **大块管理驻留。** 本地配置有 `STREAMING_CHUNK_TARGET=12`。它表示流式系统的配置目标，不能直接解释成固定 3×4 加载窗口或硬上限。
- **小块管理更新。** 开发者 2019 年公开的方案把模拟划为 64×64 小块；每块用 dirty rect 记录需要更新的范围，减少无变化区域的扫描。
- **分阶段并行。** 公开方案分四轮按棋盘式选块，并限制线程的写入邻域，避免相邻任务同时修改同一个像素。[^streaming]

这三项分别回答：**哪些世界数据留在内存、哪些材料需要计算、哪些任务可以同时执行。** “已加载”“正在模拟”“当前可见”不能视为同一状态。

本机二进制的只读 RTTI 分析进一步确认了 `IGridWorld`、`GridWorld` 与 `GridWorldThreaded` 的类层级，以及材料单元类的共享基类。它提供追踪实现的入口，但尚未确定启动时实际选择的世界实例或完整任务调度；脚本、EXE 哈希、虚表候选位置与少量字段读写的证据集中见 [[材料、地形与物理#8. 本机二进制静态分析：材料类、世界类与字段入口]]。

实体还有自身的范围管理：玩家配置带 `StreamingKeepAliveComponent`；`CameraBoundComponent` 则提供距离、数量限制，以及冻结后恢复的选项。不同实体可以覆盖配置，因此不能用某一个默认距离概括所有实体的卸载规则。[^entities]

## 4. 角色与物品如何工作：实体由组件组成

材料网格负责地形，玩家、敌人、道具等则由实体承载。实体 XML 可以声明组件、标签、子实体，并继承基础模板。[^entities]

```text
玩家实体
  ├─ 移动、控制与碰撞组件
  ├─ 生命、状态、库存等组件
  ├─ Lua 脚本组件
  └─ 手臂、披风、携带物品等子实体
```

例如 `player.xml` 继承 `player_base.xml`，再加入初始物品。公开 API 提供实体创建与销毁、组件增删、组件启停，以及按标签操作等入口。

**脚本既可以定期运行，也可以由事件触发。** `LuaComponent` 的关键字段如下：

| 字段或入口 | 作用 |
|---|---|
| `execute_on_added / execute_on_removed` | 添加、移除时执行。 |
| `execute_every_n_frame` | 每 N 帧运行；-1 表示仅添加、移除或事件执行。 |
| `execute_times / remove_after_executed` | 限制次数，或执行后移除。 |
| 受伤、死亡、拾取、交互、射击等回调 | 响应具体事件。 |
| `vm_type` | 选择共享或独立 Lua VM 等模式。 |

世界层还有初始化、更新前后等钩子。例如天气脚本从 `OnWorldPreUpdate` 更新。这些接口能确认组件与事件机制，但不能据此还原全部 C++ 系统的执行顺序。[^runtime]

## 5. 随机、时间与全局状态如何维持

原版同时使用两类随机入口：

- `SetRandomSeed(x,y)` 配合 `Random(...)`：设置随机状态后，按后续调用取值。
- `ProceduralRandom(x,y,...)`：按位置调用，生成辅助脚本用它选择权重条目、数量或偏移。[^runtime]

**需要特别注意：`SetRandomSeed` 会改变所有 Lua 脚本共用的随机状态。** 原版 `init.lua` 特意注释，天气更新不能每帧重置它，否则会影响其他脚本。天气和部分生成条件还会读取现实日期时间，所以世界种子并非所有行为的唯一输入。

全局数据也分成不同层：

| 状态层 | 主要内容与接口 |
|---|---|
| 帧与世界时间 | `GameGetFrameNum()`；WorldState 的时间、天数等字段。 |
| 环境状态 | WorldState 中的风、雾、云及目标值。 |
| 单局共享数据 | `GlobalsGetValue/SetValue`、单局 flags、SessionNumbers。 |
| 跨局进度 | `AddFlagPersistent/HasFlagPersistent` 等持久标记接口。 |

这些数据不是同一种计时器或同一个字典；它们各自完整的保存语义仍需核对。相同种子也不能直接证明材料模拟和战斗可以逐帧重放。[^runtime]

## 6. 世界如何保存：种子之外，还要保存实际状态

**种子用于生成初始内容，存档还必须承载游玩后的状态。** 本地存档已经能直接看到玩家组件、子实体及世界状态，而不是仅有一个种子。[^save]

| 状态 | 本次能够确认的内容 |
|---|---|
| 玩家与携带内容 | `player.xml` 以 Entity 为根，包含组件与嵌套实体。 |
| 世界与环境 | `world_state.xml` 包含 WorldStateComponent 及统计子实体。 |
| 会话与持久进度 | 存在 `session_numbers.salakieli`、`persistent` 等文件或目录；编码及全部语义未解析。 |
| 实际地形块 | 当前样本的 `world` 目录没有地形块，无法直接核对其编码与恢复行为。 |

社区技术记录将 `.stream_info` 对应到种子、帧数与流式状态，将 `world_[x]_[y].png_petri` 对应到地块材料及物理对象，将 `entities_[index].bin` 对应到分区实体。**这些是后续核对入口，本轮未用真实地形样本验证；`.png_petri` 也不是标准 PNG。**[^saveformat]

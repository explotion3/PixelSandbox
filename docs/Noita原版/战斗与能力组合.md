# Noita 战斗与能力组合

> [!abstract] 先抓住这条主线
> **法杖提供基础参数 → Lua 抽取并执行法术卡 → 构建本次施法与触发载荷 → 引擎生成投射物 → 碰撞产生伤害、效果与地形变化。**

| 核心问题 | 原版规则 |
|---|---|
| 一个槽位等于发射一颗子弹吗？ | 动作可以继续抽牌、修改共享状态、构建触发载荷，或执行独立功能。 |
| 连发速度只看施法间隔吗？ | 施法等待、整轮充能与法力恢复是不同限制。 |
| 触发弹命中时才决定下一张牌吗？ | 载荷在本次施法构建时就参与抽牌和法力结算，释放发生在之后。 |
| 修正器只修改弹丸伤害吗？ | 它还可改弹道、附加组件、命中效果、材料轨迹及施法反馈。 |
| 能穿过敌人就能穿墙吗？ | 穿透实体、穿过世界、破坏地形与反弹有不同参数。 |

本篇聚焦法杖执行、投射物、命中伤害与状态。角色接触环境见 [[角色与环境]]，材料破坏见 [[材料、地形与物理]]。代码可读部分直接分析 Lua；引擎接管的生成、碰撞和结算细节单独标出。

## 1. 施法由哪些层组成

| 层 | 原版入口 | 负责什么 |
|---|---|---|
| 法杖能力 | `AbilityComponent` | 当前法力、上限、恢复参数，以及是否使用 Lua gun system。 |
| 法杖基础配置 | `gun_config` | 每轮起始抽牌数、洗牌、充能时间、容量。 |
| 基础施法参数 | `gunaction_config` | 基础施法等待、散布、速度倍率等。 |
| 动作定义 | `gun_actions.lua` | 每种法术的费用、类型、次数与执行函数。 |
| 执行器 | `gun.lua` | 管理牌堆、手牌、弃牌、施法状态及充能。 |
| 投射物与目标 | 实体 XML、Projectile、DamageModel 等 | 弹丸飞行、命中、伤害、状态、爆炸及地形作用。 |

`use_gun_script=1` 会让 Ability 的默认行为改用 Lua 法杖系统；GunComponent 则在角色侧提供相关脚本管理入口。动作、投射物和受伤目标由不同数据负责。[^layers]

**XML 可以只是初值。** 普通玩家实际引用 `starting_wand_rng.xml`，其初始化脚本会再修改参数。例如当前脚本将容量选在 2～3、基础施法等待选在 9～15、充能时间选在 20～28，并选择初始法术。不能把另一个固定 starting_wand 模板当成每局最终配置。[^initial]

## 2. 一次施法怎样执行：牌堆、手牌与弃牌

`gun.lua` 明确维护三组牌与两类施法状态：[^draw]

- `deck`：等待抽取的动作。
- `hand`：本次已经执行、尚未结算的动作。
- `discarded`：已经结算的弃牌，可在后续整理回牌堆。
- `c`：当前施法参数，包括伤害增量、等待、弹道、材料和附加效果等。
- `current_reload_time`：这一轮累计后的充能时间，与单次 `c.fire_rate_wait` 分开。

本地 Lua 的主链是：

```text
_start_shot
  → 建立 root_shot，复制法杖基础参数，接收当前 mana
  → draw_shot / draw_actions：按需要抽牌
  → draw_action：检查费用和剩余次数，执行动作
  → 动作修改 c、继续抽牌或登记投射物
  → register_action / SetProjectileConfigs：把结果交给引擎
  → 手牌结算；必要时整理牌堆并 StartReload
```

非洗牌法杖按 `deck_index` 排序；洗牌分支会重排牌堆。**抽到费用不足或次数为零的动作时，它会进入弃牌，执行器还会尝试抽其他可用动作，并非整个法杖立即停止。** 未填写 mana 的普通动作在此执行器中使用默认费用 10。[^draw]

动作不一定只执行一次简单发射。原版分类包含投射物、静态投射物、修正器、多重抽牌、材料、其他、工具和被动；具体行为由各自函数决定。

## 3. 组合为什么有效：修正共享状态并改变抽牌结构

两个典型动作就能说明机制：[^actions]

- `DAMAGE` 先给 `c.damage_projectile_add` 加 0.4、施法等待加 5，再调用 `draw_actions(1,true)` 继续抽牌。
- `BURST_2` 调用 `draw_actions(2,true)`，让执行器在同一施法结构中继续抽两个动作。

因此“法杖每次施法数量为 1”表示初始抽牌预算，不等于最终只能创建一颗投射物。

以下按本地 Lua 静态追踪。条件：非洗牌、每次初始抽 1 张、法力与次数充足、没有永远施放或额外修正：

| 法术排列 | 本次发生什么 |
|---|---|
| 伤害增强 → 火花弹 → 火花弹 | 伤害增强继续抽出第一发火花弹；剩余火花弹留到下一次施法。下一次会重新建立基础施法状态。 |
| 二重施法 → 伤害增强 → 火花弹 → 火花弹 | 二重施法继续抽两个动作；伤害增强又抽出一发。两发处在同一施法状态中，并受该状态的伤害增量影响。 |
| 触发火花弹 → 伤害增强 → 火花弹 | 构建父弹，并把后两张构建成它的子载荷；父弹触发后再释放载荷。 |

普通火花弹和伤害增强费用各为 5、二重施法为 0、触发火花弹为 10。因此三种排列上述本次抽牌的费用分别是 10、15、20。它们说明抽牌关系，不能替代对最终弹道和目标伤害的运行验证。

修正器的作用域要结合本次施法状态与抽牌结构判断，不能单凭“离哪一张最近”。`draw_shot` 会在动作执行后登记该施法状态；多重施法和触发载荷会改变动作所属的结构。[^draw]

## 4. 触发与回绕：提前构建，延后释放

普通、触发和定时火花弹都使用同一份 `light_bullet.xml`，区别来自构建方式：[^trigger]

| 构建入口 | 做法 |
|---|---|
| `add_projectile` | 直接登记投射物。 |
| `add_projectile_trigger_hit_world` | 开始父投射物与命中触发，再抽取子载荷。 |
| `add_projectile_trigger_timer` | 在触发结构中加入帧数；定时火花弹当前参数为 10。 |
| `add_projectile_trigger_death` | 将子载荷绑定到父投射物死亡触发。 |

触发函数通过 `create_shot` 建立独立子状态，`draw_shot` 临时切换 `c`，完成后恢复父状态。mana 和累计充能变量仍是该执行过程共享的变量。载荷中的 `fire_rate_wait` 也写在子状态中，不能把所有子状态字段无差别加到主杖上。

**载荷准备与实际释放分开。** 它在父弹发出前已经参与抽牌和费用处理，之后由引擎在触发位置执行。

回绕也有明确边界：当允许即时重装、牌堆为空且未被禁止继续抽牌时，`draw_action` 会把 `discarded` 整理回牌堆并标记开始充能。该函数不会直接回收当前还在 `hand` 中的牌。所以回绕结果依赖此前弃牌和当前手牌，不能只看槽位循环。[^draw]

## 5. 施法速度与资源：几套限制同时存在

| 参数或机制 | 作用 |
|---|---|
| `c.fire_rate_wait` | 本次施法的等待参数。 |
| `current_reload_time` / `StartReload` | 整轮充能相关参数。 |
| `mana / mana_max / mana_charge_speed` | 当前法力、容量与恢复参数。 |
| `uses_remaining` | 单张动作的剩余使用次数。 |
| 永远施放 | 独立的 `_play_permanent_card` 入口，不按普通槽位完整执行同一路径。 |

这几项可以分别被动作修改。例如：[^timing]

- `RECHARGE` 将施法等待减 10，累计充能减 20，再继续抽牌。
- `MANA_REDUCE` 的 mana 为 -30，所以抽取时会增加 mana，同时把施法等待加 10。
- `CHAINSAW` 直接把当前 `fire_rate_wait` 设为 0，并把累计充能减 10；它不是普通的固定减法修正，执行顺序会影响结果。

有限次数主要在手牌移向弃牌时处理，受识别状态、自定义消耗逻辑和引擎回调等条件影响。永远施放入口把动作标记为 permanent、次数设为 -1，并在普通弃牌回收时排除它；它还具有专门的抽牌例外。具体引擎调用次序、最小等待和法力恢复时序不能仅由这段 Lua 确定。[^limits]

## 6. 投射物怎样飞行、碰撞与影响世界

创建后的投射物拥有自己的配置，施法器不再逐帧重新解释整副牌：[^projectile]

| 数据或组件 | 负责什么 |
|---|---|
| Velocity、Projectile 的速度与寿命 | 初始速度、重力、阻力、存活帧数等。 |
| `collide_with_world`、`penetrate_world` | 与世界材料、地形及物理对象相关的碰撞策略。 |
| `penetrate_entities`、`on_collision_die` | 命中实体后是否继续，及碰撞后的生命周期。 |
| `ground_penetration_*`、`config_explosion` | 地形穿透、爆炸挖洞与物理作用。 |
| `extra_entities` | 引入附加行为配置，例如追踪所需组件。 |
| `game_effect_entities` | 为命中效果提供配置入口。 |
| `trail_material`、粒子发射等 | 创建材料轨迹或视觉效果。 |

修正器可添加完整行为：HOMING 把包含 HomingComponent 的配置加入附加项；FREEZE 同时增加冰伤害并登记冻结效果；FIRE_TRAIL 同时登记点燃效果和火焰材料轨迹。**弹丸可以把战斗结果继续传回材料世界。**[^actions]

原版还把实体穿透与重复伤害区分开：组件文档描述 `penetrate_entities` 为穿过实体、每个实体只伤害一次；另有 `damage_every_x_frames` 处理场等持续伤害间隔。穿墙、穿人、重复命中和反弹不是同一个开关。

## 7. 命中怎样结算：伤害类型、对象与效果

### 伤害量不等于最终扣血

投射物有基础 damage、按类型伤害、暴击和击退等参数；目标的 Hitbox 可提供命中倍率，DamageModel 再配置各类伤害倍率、暴击抗性和免伤等。[^damage]

例如玩家基础模板明确设置爆炸倍率 0.35、holy 倍率 1.5、暴击抗性 1。普通火花弹 XML 的基础 damage 为 0.12；这些都是内部参数，不能直接把其中一个值当作最终 HUD 扣血量。完整叠加、暴击、免伤及取整顺序仍在引擎内。

命中后的附加效果由另一组数据描述。冻结效果包含持续帧数、禁止移动和冰冻残骸；燃烧效果又可以生成真实火焰，继续参与环境交互。效果施加与基础伤害需要分别理解，目标是否受影响还涉及抗性和内建规则。[^effects]

### 谁能被伤害、伤害归谁，也有独立数据

| 参数 | 处理的问题 |
|---|---|
| `collide_with_tag / dont_collide_with_tag` | 哪类实体参与碰撞。 |
| `friendly_fire` | 是否伤害相同 herd 阵营。 |
| `collide_with_shooter_frames` | 与施法者碰撞的专门规则。 |
| `explosion_dont_damage_shooter` | 爆炸是否伤害施法者。 |
| `mWhoShot / mShooterHerdId` | 原始施法者及阵营归属。 |
| `mEntityThatShot` | 尝试记录直接发射者，触发弹场景下可能与原始施法者不同；原文档对此字段保留测试不足的说明。 |

因此保护父弹施法者的某个参数，不能自动代表整条触发链及所有爆炸都安全。[^projectile]

最后，动作函数还能执行独立逻辑。例如 BLOOD_MAGIC 直接修改 DamageModel 的 hp，并提供负 mana 费用。它说明**并非每个法术都只是给下一颗子弹附加参数，也并非所有生命变化都通过普通弹丸命中入口发生。**[^actions]

## 分析边界与来源

> [!question]- 尚未确认的内部细节
> - Lua 登记的施法树在 C++ 中的全部存储、生成与序列化方式。
> - 修正参数在父子载荷之间的全部传播规则，及特殊法术的例外。
> - 最小施法间隔、充能结束、切杖与法力恢复的实际时序。
> - 伤害加算/乘算、暴击、免伤、冻结等在同帧的精确结算顺序。
> - 持续命中、特殊穿透、递归法术和所有永远施放交互的完整规则。

# Noita 角色与环境

> [!abstract] 先抓住这条主线
> **输入形成移动意图 → 角色组件处理速度、地形和姿态 → 环境分别作用于游泳、呼吸、浸染、摄入与伤害 → 游戏效果再改变角色能力。**

| 核心问题 | 原版的关键做法 |
|---|---|
| 人物图片就是碰撞体吗？ | 图片、地形碰撞框、受击框分别配置；站立与蹲伏还准备了不同受击框。 |
| 悬浮只是持续向上加速吗？ | 除移动参数外，还有剩余飞行量、补充速度及空中补充等待规则。 |
| 进入液体后只检查“在水里”吗？ | 移动、氧气、材料伤害和身体浸染有各自的数据入口。 |
| 沾到和喝下同一种液体，效果相同吗？ | 材料分别定义 Stains 与 Ingestion；同一材料可以走不同效果。 |
| 所有异常都通过同一种 Buff 实现吗？ | 状态列表、GameEffect 实体及内建状态处理并存。 |

本篇解释角色与可变世界的交互；地形材料规则见 [[材料、地形与物理]]，法杖和命中结算见 [[战斗与能力组合]]。以下均区分玩家基础模板、组件默认说明与运行时状态，未做游戏内运动取样。第 5 节补充了本地普通版可执行文件的静态逆向，使用【配置】【接口】【二进制】【推断】【未确认】区分证据；函数名称为分析命名，地址使用 RVA，不代表取得原版 C++ 源码。

## 1. 角色由哪些部分组成

普通玩家 `player.xml` 继承 `player_base.xml`，再加入初始库存。角色功能由多个组件共同承担：[^player]

| 组件 | 负责的角色功能 |
|---|---|
| `ControlsComponent` | 按键、鼠标、瞄准方向，以及按下状态和对应帧记录。 |
| `CharacterPlatformingComponent` | 跳跃、水平加速、速度限制、悬浮控制与游泳参数。 |
| `CharacterDataComponent` | 角色速度、地形范围、着地状态、飞行量等数据。 |
| `PlayerCollisionComponent` | 玩家专用碰撞、卡地形与压挤相关处理。 |
| `DamageModelComponent` | 生命、呼吸、材料伤害、燃烧及各类伤害响应。 |
| `SpriteStains / StatusEffectData / Ingestion` | 身体浸染、状态强度与摄入。 |
| `Kick / PhysicsPickUp / PlatformShooterPlayer` | 踢击、持物、瞄准、摄像机和进食区域等交互。 |

因此，角色拥有多种相互关联的状态：位置与速度、着地或游泳、飞行量、身体附着物、胃内材料、生命与游戏效果。某一种状态不能代替其余判断。[^components]

## 2. 怎样走过地形：地形碰撞与受击范围分开

玩家模板直接给出了不同范围：[^player]

| 范围 | 本地配置 | 作用 |
|---|---|---|
| 地形碰撞 AABB | X：-2～2；Y：-4.5～2.1 | 角色与地形碰撞相关范围。 |
| 默认 Hitbox | X：-3～3；Y：-12～4 | 用于受击判定。 |
| 蹲伏 Hitbox | X：-3～3；Y：-8.5～4 | 模板中带 `crouched` 标签，初始关闭。 |

**能够穿过多宽的洞，与攻击能否命中角色，是两组参数。** 上表是基础声明，不代表蹲伏、变形和其他效果下的最终运行时范围。

移动还配置了 `climb_over_y=4`、`platforming_type=2`，并分别记录着地、水平碰撞和湿滑地面等状态。组件文档把 `platforming_type=2` 描述为较安全的实现分支；具体跨小台阶和卡角的求解步骤仍在引擎内。[^components]

`PlayerCollisionComponent` 还设置压挤阈值，并记录卡在静态地形中的状态。这些入口与普通刚体撞击伤害不同；不能只凭 `physics_objects_damage=0` 就推导角色对所有挤压都免疫。

## 3. 跳跃与悬浮：控制参数、资源量和恢复条件

角色的移动不是单一速度值：

| 模块 | 玩家模板中的例子 | 含义 |
|---|---|---|
| 跳跃 | `jump_velocity_y=-95`、`jump_keydown_buffer=2` | 初始跳跃参数与按键缓冲。 |
| 水平控制 | `run_velocity`、`accel_x`、`turning_buffer`、X 速度上下限 | 共同影响加速、转向与速度限制。 |
| 重力 | CharacterData 的 `gravity=0`；Platforming 的 `pixel_gravity=350` | 两个组件的同类字段不能互相代替，前者为零不等于角色没有重力。 |
| 悬浮控制 | 上下速度限制、`fly_velocity_x`、`fly_speed_change_spd` | 飞行过程中的速度控制。 |
| 悬浮资源 | `fly_time_max=3.0`；运行时 `mFlyingTimeLeft` | 上限与剩余飞行量。 |
| 补充规则 | 空中补充参数 0.4、地面补充参数 6、空中等待 38 帧 | 恢复条件和速度并非一套固定规则。 |

组件文档还说明，空中等待及按键后的资源扣除参数用于限制反复轻点悬浮的收益；剩余飞行量也有存读档相关的历史修正。[^flight]

这里列的是字段和初值，不能直接拼成“角色实际水平速度”或精确飞行高度；运动公式、输入持续时间、碰撞与状态修改都参与结果。

## 4. 进入液体后：游泳、呼吸与材料接触分别处理

### 游泳改变运动

Platforming 的游泳参数区分静止、向上和向下的浮力系数，并有 `swim_drag`、`swim_extra_horizontal_drag`。CharacterData 另有 `liquid_velocity_coeff`，用于流动液体对角色速度的影响，以及浮力检查偏移。[^components]

所以“在液体里”不仅是一个减速标记，还会影响浮力、阻力和被水流带动的程度。

### 呼吸属于伤害模型

玩家开启 `air_needed=1`，初始及最大肺部空气均为 7，缺氧伤害参数为 0.6。组件文档描述：空气耗尽后产生缺氧伤害，并按时间步参与计算。这里不把参数直接解释成逐帧扣血量。[^damage]

### 材料伤害取决于角色的接触配置

玩家的 DamageModel 用两张对应列表配置“哪些材料伤害我”和“各自伤害参数”，例如酸、熔岩、毒液与部分危险岩石。组件另有最小接触材料数量、是否按最大生命比例处理等选项。[^damage]

**材料碰到角色，不等于一定形成浸染；形成浸染，也不等于伤害一定来自浸染。** 接触伤害、身体附着与呼吸需要分别追踪。

## 5. 沾染与摄入：同一种材料可以产生不同结果

材料的 `StatusEffects` 直接区分两条路径：[^materials]

| 材料 | 沾到身体 Stains | 摄入 Ingestion |
|---|---|---|
| 水 `water` | `WET` | 此定义没有配置摄入状态。 |
| 油 `oil` | `OILED` | 配置 `POISONED` 与 `FOOD_POISONING`。 |
| 有毒污泥 `radioactive_liquid` | `RADIOACTIVE` | 配置 `POISONED`。 |
| 酸 `acid` | 此定义没有配置身体浸染状态 | 配置 `POISONED`；同时存在独立接触伤害入口。 |

身体附着由 SpriteStains 相关数据承载，StatusEffectData 分别保存浸染强度、冷却、摄入状态及其材料来源。**附着强度、效果剩余时间和胃内材料数量是不同数据。**[^components]

进食则有自己的区域、频率和容量：玩家配置了局部进食范围、每帧进食参数，以及 `ingestion_capacity=7500`。Ingestion 还定义消化延迟、周期性减少和过量摄入伤害；这些参数不表示角色每帧一定吞下固定数量。API 也提供 `EntityIngestMaterial` 来执行完整摄入行为。[^ingestion]

### 状态怎样变成具体效果

`status_list.lua` 为状态配置图标、说明、是否有害及 `effect_entity`。例如 WET、OILED 指向不同 GameEffect 实体，文件中分别设定效果类型与帧数。GameEffect 又可以配置持续时间、互斥组和禁止移动。[^effects]

两个需要结合原生代码理解的情况：

- WET、OILED 等条目都能看到 `protects_from_fire=true`，但接触点燃还会执行油污、酒精等覆盖分支，见本节“燃烧怎样接入角色与沾染”。
- 状态列表的 ON_FIRE 项把 `effect_entity` 留空，而独立的点燃效果文件又确实存在。说明状态列表不是“每个状态都必须加载一个对应 XML”的完整处理器。

效果文件里的 `frames=600` 是该效果实体的时长参数，不能直接等同于身体附着物必然持续相同时间。

### 沾染的原生数据与更新节奏

【二进制】RTTI 将 `SpriteStainsSystem` 与 `StatusEffectDataSystem` 定位为两个独立的组件更新系统。前者的组件更新入口为 RVA `0x822080`，后者为 `0x824670`。可恢复的数据关系如下；偏移仅适用于本机已校验版本。[^stain_native]

| 层次 | 本机字段或偏移 | 已确认的用途 |
|---|---|---|
| 沾染组件 | `SpriteStainsComponent +0x5c` | `mData` 指向附着数据；精灵未准备好时会跳过。 |
| 附着外观 | `mData +0x18` | 逐像素的 32 位颜色缓冲，与原精灵的 alpha 掩码分开。 |
| 附着材料 | `mData +0x58` | 逐像素的 **16 位材料 ID**；零表示没有记录材料。每格只有一个 ID。 |
| 原精灵 | `mData +0x64` | 图像与 alpha 掩码，用于筛掉透明区域。 |
| 状态数据 | `StatusEffectDataComponent +0x48 / +0x54` | `stain_effects` 浮点数组与 `stain_effect_cooldowns` 整数数组。 |
| UI 数据 | 状态组件 `+0x94` | `mStainEffectsSmoothedForUI`，与即时覆盖值分开。 |

【二进制】材料贴附与统计没有对所有实体逐帧执行同样的全像素扫描。更新入口先检查实体是否带 `player_unit` 标签：带标签且当前帧号能被 3 整除时进入扫描，采用概率缩放除数 `d=2`；其余情况只在 `((frame XOR entity_id) & 15)==0` 时进入，采用 `d=1`。**玩家分支仍可能在其他帧命中后面的错帧条件**，因此不能简化为“玩家严格每 3 帧、其他实体严格每 16 帧更新一次”。纹理提交另受组件 `mState` 控制，不等于每次系统调用都重传纹理。

【推断】这种安排把非玩家实体的扫描分散到不同帧；它是原版在沾染系统中可见的负载分摊方式。是否还受实体休眠、系统调度或可见性限制，应继续追调用上层，不能由此计算整局的实际扫描成本。

### 从世界材料写入附着层

【配置＋二进制】材料有独立的沾染参数；本机通用材料构造器和 XML 读取器已对齐：

| 材料字段 | `CellData` 偏移 | 通用构造初值 | 已确认的意义 |
|---|---|---|---|
| `liquid_stains` | `+0x170` | 0 | 写入沾染的模式；更新路径会分别测试位 `1/2/4`。 |
| `liquid_sprite_stain_shaken_drop_chance` | `+0x178` | 1 | 晃落概率参数，与组件倍率、`d` 共同使用。 |
| `liquid_sprite_stain_ignited_drop_chance` | `+0x17c` | 10 | 尝试点燃时的附加脱落概率参数。 |
| `liquid_sprite_stains_check_offset` | `+0x180` | 0 | 读取为单字节；本轮未对齐其完整消费路径。 |
| `liquid_sprite_stains_status_threshold` | `+0x184` | 0.01 | 某材料的覆盖比例必须**大于**它，才向状态数组贡献强度。 |

上表初值是原生通用构造值，材料 XML 与继承链可以覆盖，不能作为所有材料的最终数值。

【二进制】扫描把精灵局部坐标经过朝向翻转、旋转和平移，映射到世界采样坐标。遇到可沾染材料且原精灵对应位置不透明时，写入颜色层和材料 ID 层。模式 `2` 的分支以材料颜色形成色斑；模式 `1/4` 走另一套灰度与 alpha 生成分支。**颜色和材料 ID 同时存在**，颜色看起来相近不代表状态相同。

【配置】水使用模式 `1`，油使用 `4`，血、黏液及有毒污泥使用 `2`。水的材料阈值采用通用初值 `0.01`，油与有毒污泥明确设为 `0.2`，变形药明确设为 `0.25`；配置来源与继承记录见证据文件。

【二进制＋推断】接触新液体时，同一附着格会被写成新材料的 ID，随后按新直方图重新统计。因此接触水可以通过**逐格覆盖旧附着物**改变油污、血污等强度。此路径没有先执行“水 + 每种污渍”的两两化学反应。它也没有在一个附着格里保存多层液体质量，不能把这种覆盖解释成完整的表面流体混合模型。

### 覆盖比例怎样变成状态强度

【二进制】组件更新尾部的算法位于 RVA `0x822D6C–0x822F83`。简化后如下；省略容器扩容和精灵坐标处理：

```text
清零本次材料像素直方图
N = 原精灵掩码中本次计入的不透明像素数
H[m] = 上述像素中，附着材料 ID 为 m 的像素数

清零当前 stain_effects 数组
for 每个非零材料 m:
    f = H[m] / N
    if f > material[m].liquid_sprite_stains_status_threshold:
        for 材料 m 的每条 Stains 状态记录 s:
            if 存在 cooldown[s] 且 cooldown[s] > 0:
                cooldown[s] -= 1
            else:
                stain_effects[s] += f
```

这里 `N` 的计数分支由原精灵掩码决定，不能换成碰撞框面积。多种材料若指向同一状态，贡献会相加；本段没有对相加结果做一次统一的 `0…1` 截断。`cooldown` 的递减发生在符合阈值的材料贡献分支，**不是此函数中无条件逐帧减一**。多个材料指向同一状态时，还可能在同次扫描中多次经过这一分支。

【二进制】状态系统另用 `stain_effects[s] >= 0.15` 判断是否达到沾染激活的候选门槛，后续还受效果配置等条件影响。材料门槛和状态门槛是两道判断：

| 只考虑一种材料的覆盖率示例 | 材料贡献判断 | 普通沾染状态判断 |
|---|---|---|
| 10% 水 | `0.10 > 0.01`，产生 WET 强度 | `0.10 < 0.15`，尚未满足这条状态激活判断。 |
| 15% 水 | 产生 WET 强度 | `0.15 >= 0.15`，满足。 |
| 20% 油 | `0.20 > 0.20` 不成立 | 这一材料没有贡献 OILED 强度。 |
| 超过 20% 油 | 贡献 OILED 强度 | 同时超过 `0.15`。 |

表格是按已恢复分支推演的例子，比例需用实际像素整数和浮点运算求得；它不是游戏内边界测试结果。

### 滴落与去除：改变的是附着像素

【二进制】普通更新的脱落分支会先检查运动/伤害模型条件，再检查原精灵掩码、已有颜色层和材料 ID。运动判定取 `VelocityComponent` 的前位置与当前整数位置，距离平方要求落在 `1…9999`；没有该组件的分支另有默认处理，不能概括为所有实体都必须移动。

特别要区分：脱落逻辑读到的是 DamageModel 的 **`mFireTriedIgniting`（`+0x228`）**，不是 `mIsOnFire`（`+0x218`）。这使尝试点燃与已经燃烧的条件有明确区别。

通过前置门槛后，概率分支可表示为：

```text
p1 = 当前 stain_shaken_drop_chance_multiplier
     × material.liquid_sprite_stain_shaken_drop_chance / d
drop = 百分比随机判断(p1)
if !drop && mFireTriedIgniting:
    p2 = material.liquid_sprite_stain_ignited_drop_chance / d
    drop = 百分比随机判断(p2)
```

【二进制】浮点百分比助手 RVA `0x9DCCF0` 使用同一 LCG 随机流，比较 `p/100 > (r/32767)×0.99999988`，是严格大于判断。两次概率判断按短路顺序执行；不能直接把 `p1+p2` 当作脱落率。外层还有一次整数随机门槛，以上也不是每帧最终脱落概率。

脱落分支把该格材料 ID、当前位置、速度及颜色交给世界生成入口 RVA `0x316CE0`，随后清零附着颜色与 ID，标记纹理待更新。**这是一条材料回到世界的生成调用，不只是让污渍变透明。** 世界端能否成功放置、拥挤时如何处理及是否严格守恒，本轮没有恢复，不能保证每次调用都新增一个可见世界单元。

【接口＋二进制】`EntityRemoveStainStatusEffect(entity, status_type_id, status_cooldown=0)` 对应入口 RVA `0x3B4EF0`：先清除会引起指定状态的附着材料像素，再清零该状态强度；冷却取旧值与请求值的较大者。清除助手 RVA `0x823170` 会逐格查材料的 Stains 状态列表，**不只是删掉效果图标**。

`EntityAddRandomStains` 则调用 RVA `0x823290`，把 amount 转成整数尝试量，在精灵区域随机找不透明、且尚未记录同一种材料的位置；每轮查找有 10 次候选上限。它直接改附着层，不要求先往世界中倒液体，也不保证 amount 等于最终新增的不同像素数。

【未确认】以上已恢复世界覆盖、晃落、尝试点燃时脱落及显式清除。尚不能宣称离开液体后的全部变化都由它们解释；本轮没有证明不存在其他干燥、效果脚本或特殊材料路径。

### 状态效果与 UI 的更新

【配置】`status_reflect.lua` 按 `status_list.lua` 的顺序调用 `GameRegisterStatusEffect`，把 `protects_from_fire`、激活时清除来源材料、效果实体、阈值、额外状态、永久标记等作为位置参数传入原生注册器。Lua 原文要求不删除或重排既有条目，以免破坏序列化；不能把列表顺序当作随意可改的显示顺序。

【二进制】状态系统先读取即时沾染强度，再更新 UI 专用数组：

```text
ui[s] += (stain_effects[s] - ui[s]) × (system_step × 5)
effects_previous[s] = stain_effects[s]
```

这里 `system_step` 指该系统读取的步长字段，未独立验证它在暂停、加速等条件下的全部取值。因此可确认的是**一阶平滑公式**，不是固定每帧衰减若干百分比；UI 的缓慢变化也不能反推附着物在做同样的质量衰减。

【二进制】普通沾染激活看 `>=0.15`；摄入另有剩余量、归一化阈值和分级选择。状态系统会查找带对应来源标识的子效果实体，必要时创建；不再满足条件或需要替换时，把旧 GameEffect 的剩余帧压到最多 1。带 `remove_cells_that_cause_when_activated` 的状态还会回调清除来源像素，变形类配置使用了这项能力。

这些分支进一步说明：XML 中 WET/OILED 的 `frames=600`、当前材料覆盖、状态是否激活、UI 显示值是不同量。效果实体生命周期的全部刷新与移除顺序仍需结合 GameEffectSystem，不能仅用这里的某一个字段代替。

### 燃烧怎样接入角色与沾染

**角色着火由 DamageModel 的独立状态管理，不能直接套用木头的 `fire_hp`。** 材料点燃、传播、需氧和燃尽的二进制算法集中在 [[材料、地形与物理#9. 原版燃烧：功能清单与关键算法]]；这里记录角色接口，避免把组件文档误称为已恢复的原生算法。

| 字段 | 原版组件说明中的默认值与职责 |
|---|---|
| `is_on_fire` / `mIsOnFire` | 默认 0，公开配置与内部着火状态。 |
| `fire_probability_of_ignition` | 默认 0.5；说明明确 0 表示不会被点燃；玩家模板覆盖为 1。 |
| `fire_how_much_fire_generates` | 默认 4；说明为着火时每帧生成火粒子的数量。 |
| `fire_damage_ignited_amount` | 默认 0.0003，着火伤害参数。 |
| `fire_damage_amount` | 默认 0.2，火伤害参数；玩家模板也设为 0.2。 |
| `mFireProbability` | 默认 100；说明为不能继续引燃其他东西时降低。 |
| `mFireFramesLeft` / `mFireDurationFrames` | 剩余与总着火帧数状态；不能从默认零推出实际持续时间。 |
| `mFireTriedIgniting` | 记录是否尝试点燃的内部状态。 |
| `mFireDamageBuffered` / `mFireDamageBufferedNextDeliveryFrame` | 缓冲火伤害及下次交付帧；说明提到减少大量实体同时受火伤的开销。 |

上表为**接口与配置证据**。本轮补充了下述沾染保护、接触点燃时长及计时器递减分支，火伤害缓冲和完整命中公式仍未恢复，不能把两个 damage 数值直接当成已确认的每帧扣血公式。原版组件说明、玩家模板和状态表保存在证据文件中。[^role_fire]

`effect_on_fire.xml` 另外定义 `ON_FIRE` 效果、`frames=100`、真实火粒子发射器、默认关闭的烟发射器和循环音效。这个效果实体的 100 不代表所有角色统一燃烧 100 帧，ON_FIRE 状态表条目的空 `effect_entity` 也不能当作不存在内建燃烧的证据。

【配置＋二进制】状态表中 WET、OILED、BLOODY、SLIMY、RADIOACTIVE，以及另一个 HYDRATED 条目都有 `protects_from_fire=true`。原生保护谓词 RVA `0x824F50` 遍历沾染状态：**只要某一项强度 `>=0.15` 且该项保护标记为真，就返回真**。不是把所有保护液体的覆盖率先相加；它也不使用 UI 平滑值。

【二进制】材料接触检查 RVA `0x6B6010` 在判定本次尝试点燃后，计算候选燃烧时间。分支顺序已核实：

```text
t = 保护谓词成立 ? 0 : 12
if ALCOHOLIC 强度 >= 0.15: t = 20
if OILED 强度 >= 0.15:     t = 30
if 另一个 GameEffect 计数条件成立: t = 0.25
candidate_frames = round(t × 60)
mFireFramesLeft = max(mFireFramesLeft, candidate_frames)
mFireDurationFrames = max(candidate_frames, mFireFramesLeft)
若剩余帧 > 0，则设置 is_on_fire
```

最后一个条件定位为本函数取得的 GameEffect 计数数据 `+0xb8 > 0`，**本轮未可靠命名其效果身份**，不擅自写成某个天赋。此公式也以“已经触发本次尝试点燃”为前提，不代表任意碰到火焰都无条件着火。

这解释了保护字段与油污的关系：**油污会在通用保护判断之后，把候选时间覆盖为 30×60=1800 个内部帧**；酒精覆盖为 1200 帧，普通无保护分支为 720 帧。只有保护、没有这些覆盖条件时，候选值为零；由于使用 `max`，它不会在此处直接把已有燃烧剩余帧清零。

【二进制】已着火分支另在 RVA `0x6B7C68–0x6B7CB7` 计算本次计时变化：

```text
delta = 保护谓词成立 ? -2 : -1
if OILED 强度 >= 0.15: delta += 1
mFireFramesLeft += delta
```

所以保护会加快这一分支的计时消耗，油污又有额外补偿；**“油污让总燃烧时间更长”和“油污每次计时减得更慢”不是可以互换的解释**。这里的 720/1200/1800 是候选内部帧，更新频率、继续接触火源及其他效果都会影响墙钟持续时间，未做游戏内计时验证。终止分支还检查 `mFireProbability`，不能只凭这一行倒计时描述所有结束条件。

粒子发射器的 `fire_cells_dont_ignite_damagemodel` 仍可控制真实火单元是否引燃 DamageModel；材料燃烧、角色尝试点燃、角色着火及附着物脱落需要分别追踪，不能仅依据看见火焰就判定一定能点燃角色。[^role_fire]

## 6. 交互、生命与死亡如何接回角色

踢击有独立的 `KickComponent`，包含作用范围、伤害、击退和物理踢力；物体拾取使用 PhysicsPickUp，瞄准和发射位置通过相关组件与 Hotspot 提供。它们与法杖施法共享角色，但不都通过同一法术动作入口。[^interaction]

生命变化也由多个规则组成：

- 玩家模板的 `hp=4` 是内部初值；不能当作 HUD 上显示的 4 点生命。
- 玩家关闭普通摔落伤害：`falling_damages=0`。这不替代其他环境伤害判定。
- `invincibility_frames=60` 是模板初值；文档说明其为正时免伤，不能据此认定每次受击都重新获得 60 帧无敌。
- 冻结效果文件设置 `disable_movement=1`。角色即使有剩余飞行量，也仍要经过效果对移动能力的限制。
- 世界初始化脚本的玩家死亡钩子会销毁库存物品并触发 Game Over；死亡流程还涉及伤害模型和残骸等，不能只理解为删除角色实体。[^damage][^effects][^death]

一个水池场景就能同时连接这些系统：移动组件处理游泳，伤害模型处理呼吸，水的材料配置提供 WET 浸染；离开水面后，运动状态与身体附着物的变化不必同步。后续受到冻结或其他效果时，又会反过来约束移动能力。
